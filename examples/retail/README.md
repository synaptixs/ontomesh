# First-Contact Demo — Engineering Guide

How to run and interpret the "does an ontology actually help LLM output?" demo. Companion to [test-plan.md](test-plan.md).

**TL;DR for engineers.** Run `./demo.sh`. Open `output/demo/comparison.html`. That's the full matrix. For the 5-minute exec version, open `output/demo/executive.html`.

**TL;DR for executives.** Open `output/demo/executive.html` — it's a single page, three examples, no jargon.

---

## Two audiences, two views

| Audience | File | What they see | Time to read |
|---|---|---|---|
| Executives / business stakeholders | `output/demo/executive.html` | One page · 3 hand-picked before/after pairs · plain-English "what changed" annotations · no code | ~3 min |
| Engineers / architects | `output/demo/comparison.html` | Full 8-question × 2-vendor × 2-mode matrix (32 cells) · SHACL/PROV-O/IRI pills per grounded cell · ground-truth citations · links to every artifact | ~15 min |
| Both | `output/demo/reports/toolkit_report.html` | Standard toolkit report — ontology, shapes, semantic-loss findings, 43 SPARQL CQ results, governance scorecard | ~5 min |

---

## Prerequisites

- Python 3.10+
- SQLite 3 (bundled with Python)
- `pip install anthropic openai` (only needed for live mode)
- Optional: `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` env vars

The demo runs in **illustrative mode** without API keys — scripted answers derived from the real ground-truth rows stand in for the live LLM responses. Comparison logic, SHACL gating, semantic-loss detection, and every artifact generated by `toolkit.py` are still 100% real; only the LLM-produced text is pre-authored. The comparison HTML shows a banner so no one mistakes illustrative for live.

## One command

```bash
./demo.sh              # auto-detects API keys, illustrative fallback
./demo.sh --live       # require live API keys, fail loudly if missing
./demo.sh --fresh      # wipe output/demo/ and db/demo.db, rebuild everything
./demo.sh --open       # also open the executive view in a browser
```

The runner chains five steps:

1. Build `db/demo.db` from `db/demo.sql` + `db/demo_seed.sql` (retail schema, 8 domain tables, ~60 rows, 17 `ontology_metadata` annotations)
2. Run `toolkit.py --db db/demo.db --out output/demo/` (generates OWL + SHACL + JSON-LD + SKOS + 43 CQ tests, ~3 seconds)
3. Run `examples/retail/scripts/demo_baseline.py` — 8 questions × 2 vendors × raw SQL rows + plain prompt
4. Run `examples/retail/scripts/demo_grounded.py` — 8 questions × 2 vendors × `RuntimeClient.ask(flavor='retail')`
5. Run `examples/retail/scripts/demo_report.py` — reads the cache, writes `comparison.html`, `executive.html`, `comparison.csv`

Step 2 takes ~3 seconds. Steps 3+4 combined run in under 30 seconds in live mode (16 total API calls per vendor × 2 = 32 calls).

## The retail schema — why it's designed this way

`db/demo.sql` is small on purpose (≈120 lines) but deliberately structured to produce interesting ontology findings. Four design choices worth pointing out during the demo:

1. **`status` appears on four tables** (`customers`, `orders`, `invoices`, `payments`) with different valid values on each. The word "Active" is valid only on `customers`. This surfaces in Q1, Q7.
2. **`order_events` is an event table** with `event_type` as discriminator — the toolkit auto-generates one OWL subclass per distinct event_type value. This surfaces in Q3, Q6.
3. **`order_events.derivation`** records PROV-O provenance (`MEASURED` vs `INFERRED`). Row 23 is an INFERRED cancellation on order 9 (driven by a fraud-rule, confidence 0.72) that coexists with a MEASURED cancellation (row 16). Q6 is designed specifically around this.
4. **`order_events` has no FK to an agent table.** The mapping-generator flags this as `IMPLICIT_ACTOR` → CRITICAL. `actor_party` is a free-text column ("customer", "carrier", "fraud-rule"). The semantic-loss report calls out exactly this remediation.

## The 8-question bank (`examples/retail/scripts/demo_questions.py`)

Each question is paired with a `why` annotation so you can explain the deliberate construction:

| ID | Question | Design intent |
|---|---|---|
| Q1 | *Which customers are Active?* | Ambiguous vocabulary — "Active" is valid on three tables |
| Q2 | *Show me overdue invoices and the customers who owe them.* | Cross-table join; grounded answer returns JSON-LD subgraph |
| Q3 | *Which orders never reached the Delivered state?* | snapshot status vs lifecycle event — grounded reads `OrderEvent`, baseline reads `orders.status` |
| Q4 | *Are there any disputed invoices with reversed payments?* | State-machine intersection across two tables |
| Q5 | *Full customer-to-payment chain for order 7?* | FK→object-property traversal; grounded returns stable IRIs |
| Q6 | *Which cancellation events were inferred rather than measured?* | PROV-O derivation vocabulary — baseline has no name for this concept |
| Q7 | *List active orders whose shipment is missing.* | Vocabulary mismatch: `orderStatus` has no "Active" SKOS concept |
| Q8 | *Summarise customer 1's standing in one sentence.* | Free-form; tests whether grounded output remains SHACL-valid while reading naturally |

## The runtime path (`examples/retail/scripts/demo_grounded.py`)

Calls `RuntimeClient.ask(question=..., flavor="retail")`. The pipeline inside that one call:

```
question
    │
    ▼
FlavorRegistry.get("retail")           ← runtime/flavors/retail.json (auto-discovered)
    │
    ▼
Grounder.query_and_ground(db_tables)   ← runtime/grounder.py
    │  retrieves rows from customers / orders / invoices / payments / order_events
    │  serialises each as a JSON-LD node with @type = retail:Customer / retail:Order / …
    │  every @id is a stable IRI
    ▼
InputGate.screen()                     ← runtime/input_gate.py
    │  SHACL-validates every grounded record; rejects malformed or low-confidence
    ▼
PayloadAssembler.assemble()            ← runtime/assembler.py
    │  five components: system prompt · flavor definition · grounded data
    │  · PROV-O context · question
    ▼
anthropic_adapter.py | openai_adapter.py
    │  Anthropic adapter uses prompt caching on the system prompt
    ▼
OutputGate.validate_and_stamp()        ← runtime/output_gate.py
    │  SHACL-validates the response JSON
    │  stamps PROV-O: wasGeneratedBy + generatedAtTime + confidence + derivation
    │  inserts into ObservationRecord store
    ▼
{answer, valid, observation_iri, prov}
```

The `retail` flavor (`runtime/flavors/retail.json`) declares the `owl_classes`, the `db_tables` Grounder walks, and a `system_prompt_hint` that explicitly tells the LLM to disambiguate `status` by OWL class. That hint is the secret sauce — it's why both vendors give equivalent grounded answers.

## Reading `comparison.html`

Each of the 8 questions renders as a card with:

- **Question header** + the `why`
- **Ground truth** — computed once from `db/demo.db` (in `illustrative.json`)
- Per vendor (Anthropic, OpenAI):
  - **Baseline** card (peach background) — raw rows + plain prompt, no ontology
  - **Grounded** card (mint background) — `RuntimeClient.ask(flavor="retail")` with SHACL/PROV-O/IRI pills
- **Why it matters** footer — the teaching moment for that question

Pills on the grounded cards:

| Pill | Meaning |
|---|---|
| `SHACL ✓` / `✗` / `—` | Output shape validation passed / failed / not available (illustrative) |
| `PROV-O ✓` / `—` | Response stamped with model + timestamp + confidence + derivation |
| `ObservationRecord` | Response stored back into the DB as a first-class fact |

Source badges: `live` = real LLM output from cache; `illustrative` = scripted fallback from `illustrative.json`; `missing` = neither (shouldn't happen).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Banner says "Illustrative mode" even with keys set | Keys weren't in the env when `demo.sh` ran | Export keys first, then `./demo.sh --fresh` |
| `RuntimeClient` error about missing flavor | `runtime/flavors/retail.json` not present | Re-pull branch or re-run `demo.sh` from repo root |
| Toolkit phase errors about missing ROBOT | Optional reasoner absent | Ignore — the SPARQL CQ path runs without it |
| SHACL pills blank on all grounded cells | Ran in illustrative mode | Re-run `./demo.sh --live` with real keys |
| One vendor's cell shows an error string | Transient API error | Re-run; cache will only overwrite that cell |

## Extending the demo

- **Add a question** — append to `QUESTIONS` in `examples/retail/scripts/demo_questions.py` and a matching entry in `illustrative.json`. Re-run.
- **Add a vendor** — extend `VENDORS` in `examples/retail/scripts/demo_report.py` and add a matching call branch in `demo_baseline.py` / `demo_grounded.py`. Any adapter in `runtime/adapters/` works.
- **Swap the domain** — replace `db/demo.sql` + `db/demo_seed.sql` and edit `runtime/flavors/retail.json`'s `owl_classes`, `db_tables`, and `context_terms`. The rest of the pipeline is schema-agnostic.
- **Tighten SHACL** — add NodeShapes to `output/demo/shapes/enterprise-shapes.ttl`. The grounded path's `OutputGate` will enforce them.
